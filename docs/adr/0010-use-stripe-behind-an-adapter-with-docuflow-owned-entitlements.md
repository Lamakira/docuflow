# Use Stripe behind an adapter with DocuFlow-owned entitlements

DocuFlow bills through Stripe Billing behind a replaceable BillingProvider adapter, with DocuFlow as merchant and Stripe Tax enabled from launch. Every Workspace — individual or organization — runs one machinery: a Subscription is a Plan plus purchased seat capacity, where seat increases apply immediately with proration and decreases apply at period end, floored at active Billable Seat consumption. A DocuFlow-owned versioned Plan registry maps plan keys to entitlement values; effective entitlements are a pure function of billing state, plan, and registry version, with audited per-workspace overrides and grandfathering by version pinning. The billing state machine (Trialing, Active, PastDue, ReadOnly, cancel-at-period-end) is DocuFlow-owned: trials carry no card and no Stripe objects, dunning retains full access until the terminal outcome, and ReadOnly is an entitlement outcome enforced centrally by capability write-classification. Webhooks land in a signature-verified, deduplicating inbox; durable workers re-fetch the authoritative Stripe object into a provider-neutral projection that recomputes entitlements, bumps the authorization version, and emits outbox consequences, with daily drift-alerting reconciliation. Checkout and payment methods stay on hosted Stripe surfaces while plan and seat changes live only in DocuFlow's UI; the migrated legacy workspace gets a pinned legacy plan with no Stripe objects. Paddle's merchant-of-record path (expensive, high lock-in), auto-scaling seats (unpredictable spend, breaks fail-closed exhaustion), Stripe-modeled trials and Stripe-driven entitlements (provider state as authorization truth), and seatless individual plans (two billing shapes everywhere) were all rejected.
