# Expose three contract surfaces with thin signed webhooks

DocuFlow exposes three contract surfaces on its one HTTP runtime — a private web BFF deployed in lockstep with the web client, a separately versioned desktop sync API, and a public `/api/v1` with URL major versions and additive-only evolution — all calling the same module interfaces. Public access authenticates with per-Service-Account static API keys mapped to PrincipalContext, is rate-limited by token bucket per Service Account plus a per-Workspace aggregate whose limits read from the Plan Registry, and honors optional Idempotency-Key stored-response replay. Webhooks are workspace-owned Webhook Endpoints fed by the transactional outbox through an explicit public event allowlist, HMAC-signed, delivered at-least-once and unordered with ~72h backoff retries, auto-disable on sustained failure, and replay; payloads are thin — event type and resource ids only — so consumers re-authorize by fetching current state and payload data stays out of consumer logs. The desktop protocol is agent-initiated HTTPS with a handshake carrying clock anchor, Tracking Policy version, minimum protocol version, and directives; it versions independently with a 12-month/two-version support window plus a further 6-month drain window in which below-minimum agents can still upload queued offline work. Previous public majors live at least 12 months after a successor with Deprecation/Sunset signaling; errors use RFC 9457 problem+json with stable types and request ids, pagination is cursor-only, ids are opaque, and timestamps are RFC 3339 UTC. One versioned API for every client, OAuth2 client-credentials at launch, fat webhook payloads, ordered webhook delivery, a persistent desktop push channel, and offset pagination were all rejected — stability promises would tax web iteration, and offline work must never be held hostage by connectivity or version hygiene.
