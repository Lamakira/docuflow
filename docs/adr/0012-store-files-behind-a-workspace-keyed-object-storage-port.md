# Store files behind a workspace-keyed object-storage port

Native Document content stays in PostgreSQL rows while Files and derived artifacts live in an S3-shaped object store behind one shared infrastructure port, with Knowledge owning Document/File aggregates and Activity owning evidence metadata. Object keys are immutable, ID-only, and workspace-prefixed (`ws/{workspaceId}/files/{fileId}/{versionId}`, derived artifacts under `derived/`, installers under `system/`); project scope and filenames live only in database metadata. Uploads go direct to storage through authorized two-phase signed-PUT slots with finalize verification; downloads are short-lived audit-logged signed GETs issued only after backend authorization, with proxy streaming retained per sensitivity class. Versioning is app-owned on both planes — Document revision rows and immutable File version objects — with provider versioning as an ops safety net only. Derived artifacts are generated eagerly by outbox-driven durable workers, inherit source access, and never block availability. User uploads pass a fail-closed scan state machine (`pending → uploaded → scanning → available | quarantined | rejected`); agent screenshots are a documented exemption. Deletion is two-phase everywhere: item Trash with a 30-day restore window then an idempotent purge cascade across rows, objects, derived artifacts, and indexes; workspace deletion freezes for 30 days then sweeps the workspace prefix. Erasure primitives and a purge-blocking hold flag live in the port; policy matrices and RPO/RTO values are deferred to the compliance and hosting decisions. Legacy objects keep their existing keys with the database row as key authority; `company_documents` splits into Document and File rows preserving legacy IDs. Storing native documents as objects, provider versioning as the domain model, a dedicated Storage domain module, proxying uploads through the API, and an upfront mass re-key were all rejected.
