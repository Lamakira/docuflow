# Build in a parallel environment with a snapshot-rehearsed cutover

Amends ADR-0017. The nine phases, their ordering, and their discipline — expand/contract deploys, temporary flags, verifiers, evidence trail — stand unchanged, but they execute in a fully isolated parallel environment rather than against the live production deployment. This repository is a separate copy with no link to the production repository or its Replit deployment, and it must never contain production credentials, production URLs, or any data-plane connection to production systems: the database is a new Neon account, and hosting, object storage, the evidence account, identity, and billing all use fresh accounts and secrets provisioned for this effort. Production data enters this environment only as restored snapshots — logical database exports loaded into scratch branches of the new Neon account and object-store copies into R2 — so every seed, backfill, classification, and import runs first, and repeatedly, against rehearsal data.

Three ADR-0017 mechanics change shape as a consequence. The Phase 2 hosting lift becomes standing up the parallel environment with no production traffic on it. The live-drain mechanics — the Clerk dual-auth session drain window and the GCS-to-R2 dual-write window — presumed migrating a live system under its users and are replaced by snapshot rehearsal of the same transformations. Production cutover becomes one late, rehearsed event inside an announced freeze window: final export and import from the old stack, a full run of the already-rehearsed migration pipeline, verifiers green, then the traffic switch and forced desktop-fleet update to the new environment; the old production stack keeps running untouched as instant rollback until confidence is established, and is retired only afterwards. Evolving the live production deployment through the phases, as ADR-0017 originally described, was rejected once full isolation became the mandate — the trade accepts one larger, rehearsed cutover day in exchange for never exposing production to in-flight migration work.

Amended since: ADR-0021 keeps the compute on Replit, so this isolation is two separate Replit projects with disjoint secrets and the North-American placement of Replit development environments makes rehearsal a residency constraint as well as an isolation one; and ADR-0022 settles the object plane this decision left open — the environment is given its own R2 bucket in Phase 2, the object-store copy named above is specified as an operator-run, key-preserving snapshot ordered after its paired database export and scrubbed of absolute production storage URLs, and the GCS dual-write this decision retired is replaced by copy reconciliation.

Also since: the desktop release path is **disarmed rather than excepted**, closing the conflict `docs/migration/phase-1-stabilization.md` recorded and deliberately did not elevate into a Phase 1 gate ([#60](https://github.com/Lamakira/docuflow/issues/60), 2026-08-14). This decision forbids production credentials and URLs in this repository, and `.github/workflows/desktop-release.yml` exists to reach real users with a signing identity, a public installer bucket, and the production backend's URL and token — so the two could not both stand. **The conflict turned out to be prospective and not actual**, and the enumeration this ticket required is what established it: zero Actions secrets configured on this repository, zero on the old `techma-documentation-platform` repository, no `desktop-agent-v*` tag on either, no GitHub Release on either, and no run of the workflow, ever. Nothing was removed because nothing was there; what was removed is the **automatic path** — the `push` tag trigger — and the header that instructed a reader to create the four credentials that would have made this decision false, in a repository that is public. Desktop releases in fact happen through operator-run `scripts/publish-release.sh` from a machine holding its own credentials, which never involved this workflow and is untouched.

The disarm is structural rather than a flag, which is what makes it checkable: every publishing step is gated on `github.event_name == 'push'`, an event the workflow can no longer receive, and `workflow_dispatch` cannot satisfy that gate however its inputs are set. One step escaped that property and is the reason this amendment is worth reading rather than filing — the macOS **build** step carried the Apple signing secrets and **no gate at all**, so removing the trigger would have left a production signing identity consumable by any manual run. Those four secrets are gone from the file rather than gated, because signing is the production-reaching half and building is the half worth keeping. A grep-based check called the file clean and a parser found the hole, which is why `tests/smoke/desktop-release-workflow.test.ts` parses the workflow: a credential boundary guarded by a regex over YAML is a boundary that is believed rather than held.

Re-arming is a decision and not an edit. It needs an ADR or an amendment here naming the credential scope, and the trigger afterwards — never the reverse. Two things are recorded rather than settled: the desktop agent's own distribution is therefore frozen for the length of the migration, which is a cost this decision accepts rather than a detail; and the four Apple secrets are named here because a decision that removes a capability should say what it removed, so that whoever restores it knows what to ask for.
