# Gate agent project access on existence until Workspace scoping lands

Records a deliberate, temporary exception to ADR-0004 and ADR-0006 (#31). The desktop agent's `/api/agent/tasks` (read and create) and `/api/agent/timer/start` check only that the CRM project id resolves; they no longer require a Membership row on it or ownership of the underlying project. Those three routes carried the product's only membership gate, while `GET /api/agent/projects` listed every project — `storage.getCrmProjects` takes a user id and ignores it — and the SPA's `/api/tasks`, `POST /api/tasks`, and `/api/time-tracking/start` never checked membership at all, so the gate refused on the desktop exactly what the same User could do in the browser a moment later, once per project the picker offered. Removing it is a parity fix rather than a widening: no access became possible that a browser session did not already have, and the picker stops offering what the next call refuses.

This contradicts ADR-0004, which rejects "the current global-organization assumption ... because it cannot provide tenant isolation", and ADR-0006, which puts an immutable `workspace_id` on every Workspace-owned row and enforces scoping in depth. Both stand; nothing here reopens them. What the exception records is that project visibility today is Workspace-wide by omission — the rejected assumption, still in the code — and that three agent routes now depend on it openly rather than one of them papering over it. Tightening the agent alone was rejected because it would leave the SPA wide and the desktop narrow for the same User, which is the disagreement #31 reported, inverted rather than fixed; tightening both surfaces was rejected as the Workspace-permissions design ADR-0006 describes and Spec #18 owns, not a desktop bug fix. When that design lands, the boundary belongs on both surfaces in one change: these three routes, the SPA's task and time-tracking routes, and the characterization suites that freeze the current answer (`tests/characterization/agent-workspace.test.ts`, `agent-timer.test.ts`) move together, and this decision is superseded. Ownership still guards a time entry once it exists — pause, resume, and stop refuse another User's entry — and that is untouched.
