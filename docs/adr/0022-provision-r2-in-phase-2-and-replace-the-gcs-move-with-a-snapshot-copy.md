# Provision the parallel environment's R2 bucket in Phase 2 and replace the GCS move with a snapshot copy

Amends ADR-0017 and completes ADR-0018 on the object plane, resolving the conflict recorded in [#51](https://github.com/Lamakira/docuflow/issues/51). ADR-0017 has Phase 2 lift hosting "while GCS keeps serving objects" and defers the GCS → R2 move to Phase 6; ADR-0018 forbids any production credential, production URL, or data-plane connection to production from this environment, and GCS is production. The parallel environment therefore gets its own Cloudflare R2 bucket — `eu` jurisdiction, per the ADR-0016 storage line ADR-0021 left standing — provisioned with the Phase 2 accounts ([#52](https://github.com/Lamakira/docuflow/issues/52)) and wired in [#59](https://github.com/Lamakira/docuflow/issues/59), and it never speaks to GCS at all. Waiting until Phase 6 is not among the options: `server/config.ts` aggregates absent object-storage variables into a boot failure, and the only credential that satisfies them today is a Google service-account key, so a Phase 2 environment without its own bucket is an environment that does not start; and storage is not a corner of the product that could wait, because browser upload and download in `routes.ts`, content extraction in `contentExtraction.ts`, desktop screenshot upload in `agentRoutes.ts`, and installer delivery in `downloadRoutes.ts` all sit on that one client. Deferring to Phase 6 would leave four phases of rehearsal exercising nothing that touches a File, which makes ADR-0018's "every seed, backfill, classification, and import runs first, and repeatedly, against rehearsal data" false for the whole object plane.

Before Phase 6 the bucket holds two things: everything the environment writes while rehearsing, and a restored object snapshot that is the object half of ADR-0018's snapshot pair. The copy is out-of-band and operator-run, never a job in this environment — a read-only production-side credential and a write-scoped destination credential meet only in the operator's session, on a machine that is neither this repository, its CI, nor its Replit Secrets, and the transfer reads production and writes R2 with no path in the other direction. It is key-preserving: destination object name equals source object name, with no re-keying, no flattening, and no prefix rewrite, because ADR-0012 makes the database row the key authority and today's rows already carry bucket-relative identity — `normalizeObjectEntityPath` reduces uploads to `/objects/{entityId}` beneath `PRIVATE_OBJECT_DIR`, and screenshots carry a `storage_key`. The bucket name and that prefix are configuration, not identity, which is what lets a restored database resolve against a differently named bucket. The object copy is taken at or after the database export it is paired with, never before: objects are immutable and creation-only, so a later copy is a superset of what the earlier export names, while the reverse order manufactures dangling keys that are an artifact of sequencing rather than of the migration. The snapshot is workspace content, so ADR-0021's residency constraint on the database snapshot binds it identically — the bucket carries the `eu` jurisdiction, and no copy of it may be loaded into a Replit development environment, which runs in North America regardless of where the project publishes. The copy manifest — keys, sizes, checksums, counts, and both snapshot timestamps — is the Phase 2 evidence artifact under ADR-0017's evidence rule, and it names no credential and no bucket secret.

Preserving keys is necessary and not sufficient, and the exception is named here because it re-creates the connection ADR-0018 forbids with no credential involved at all. `desktop_releases.storage_url` stores an absolute `https://storage.googleapis.com/BUCKET/OBJECT`; `downloadRoutes.ts` validates that literal host when a release is published, branches on it when reporting availability, and redirects clients straight at the stored value. A restored snapshot imported unscrubbed therefore points the parallel environment's own download endpoint at production storage, as data. The seed scrubs absolute storage URLs out of the restored database rather than only preserving keys, and the scrub is a check across every column that can hold one, not a fix to the one table known today. The parallel environment's installers are its own build artifacts, so those rows are rewritten to its own objects or left reporting the platform unavailable until the desktop release workflow is settled ([#60](https://github.com/Lamakira/docuflow/issues/60)).

Four ADR-0017 Phase 6 mechanics change shape as a consequence. **The dual-write window is deleted**: it existed to keep a live GCS and a filling R2 consistent while readers moved across, but it would require production *write* credentials held by the environment least permitted to hold them, and there is no second live writer to stay consistent with, since this environment's objects are its own. **The read flip is deleted**: there is nothing to flip from, the environment reads R2 from its first byte, and the moment anyone stops reading production objects is ADR-0018's traffic switch itself rather than a storage flag inside a phase. **The bulk copy survives and changes role**, from a one-time production migration step into the rehearsal seed above — run first in Phase 2, re-run whenever rehearsal data is refreshed, and run once more as the final delta inside the announced cutover freeze, which is the repetition ADR-0018 trades a larger cutover day to buy. **Shadow-read comparison, which ADR-0017 reserved for authorization and storage-port swaps, has no storage-port swap left to compare** and is replaced by copy reconciliation: the source manifest against the destination listing, plus a dangling-key verifier asserting that every storage key the restored database names resolves in R2 — objects R2 holds that the database does not name are expected, because they postdate the export, while a key the database names and R2 lacks is a failure. What stays in Phase 6 is the Document/File split, unchanged, now operating on objects already in R2 with their keys intact.

The accepted cost is that the provider swap moves into Phase 2 as code and not only as procurement. `server/objectStorage.ts` is a `@google-cloud/storage` client whose `File` type reaches into `objectAcl.ts`, whose ACL policy lives in GCS custom metadata, and whose signing is GCS V4, so pointing this environment at R2 means writing the S3-shaped adapter before the Knowledge module exists to own it. The line is drawn at the provider: Phase 2 replaces what sits behind today's `ObjectStorageService` seam and preserves today's behavior, while ADR-0012's port surface — two-phase slots with finalize verification, the fail-closed scan state machine, the purge cascade, the hold flag — still lands with the Phase 6 carve-out that owns it, and [#59](https://github.com/Lamakira/docuflow/issues/59) is scoped to the swap rather than to the port. Five alternatives were rejected. No object storage until Phase 6, the literal ADR-0017 reading, was rejected because the application does not boot without a storage credential and the rehearsal it protects would cover nothing that touches a File. Pointing this environment at production GCS read-only was rejected because a read-only production credential is still a production credential in the environment's secret store, and it leaves production objects one lifecycle rule or one destructive rehearsal away from an environment built to be reset repeatedly. Keeping the Phase 6 dual-write with this environment as the second writer was rejected outright, as it needs production write credentials. A fresh GCS bucket here, so that the GCS → R2 swap stays a rehearsable step, was rejected because that step no longer exists in production — there is no in-place provider swap left to rehearse, only a copy to verify — and it would buy the rehearsal with a second provider, a second credential, and a second bill, the trade ADR-0021 already refused. A synthetic-only seed was rejected because it would prove the adapter works and nothing about identity, and legacy key preservation is precisely the property the seed exists to test.

Amended since: ADR-0023 changes the provider and nothing else. The parallel environment's bucket is **Replit App Storage**, not Cloudflare R2 — App Storage is Google Cloud Storage-backed and reachable through the `@google-cloud/storage` client this repository already uses, so the S3-shaped adapter this decision scheduled is not written, `server/objectStorage.ts` keeps its current client, and the accepted cost recorded above — "the provider swap moves into Phase 2 as code and not only procurement" — is withdrawn. Residency is met by the publishing geography, which ADR-0021 records as colocating compute, database, and Object Storage, rather than by the `eu` jurisdiction setting named above. Everything else here stands unchanged and none of it depended on the vendor: the operator-run, key-preserving snapshot copy ordered at or after its paired database export, the prohibition on loading any copy into a North American Replit development environment, the copy manifest as the Phase 2 evidence artifact, the dangling-key verifier, the deletion of the dual-write and read-flip mechanics, and the Document/File split remaining in Phase 6. One hazard this decision identified gets **worse** and the change is the reason: `desktop_releases.storage_url` stores an absolute `https://storage.googleapis.com/BUCKET/OBJECT` and `downloadRoutes.ts` validates that literal host, so a GCS-backed destination now shares the host an R2 destination would not have, and an unscrubbed production row passes a host check that would previously have caught it — only the bucket name distinguishes them, which makes the scrub the sole remaining guard rather than one of two. The rejection recorded above of "a fresh GCS bucket here" is superseded on its own terms: it was refused as "a second provider, a second credential, and a second bill", and App Storage is none of the three.
