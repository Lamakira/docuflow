# Let the Workspace Role govern Administration and keep the platform directory separate

Administration is authorized by the Workspace Role, not by a Capability and not by the global `users.role` column (#238). Owner and Administrator reach it; Member does not. `server/workspaceRole.ts` is the one place that decides, and the four surfaces that had each grown their own copy of the same check — Billing, Service Accounts, Webhook Endpoints, Invitations — now share it with the `/api/admin/*` routes that never had it.

This resolves a contradiction between CONTEXT.md and the code rather than inventing a third answer. CONTEXT.md defines **Capability** as "a named permission granted through a workspace role that determines which destinations and actions a member may access", which reads as though every destination is a Capability's to govern. Administration never was one: `capabilities` holds `view_daily_updates` and five Public API grants a Service Account carries, and nothing else, so the refusal a Member met — "You do not have the Administration Capability. _X_ (Owner) can grant it." — named a row that does not exist and offered a grant nobody, Owner included, could make. The alternative was to mint an `administration` Capability row and grant it to `owner` and `administrator` in every Workspace. It was rejected because the grant would be unrevokable in practice (an Owner who revoked it from the Owner Role would lock the Workspace) and because it would be the only Capability that is really a Role in disguise, while four working surfaces already authorized on the Role. The glossary's sentence is therefore narrowed, not contradicted: a Capability governs destinations and actions **within** a Workspace Role's reach; the Role itself decides which destinations are in reach at all. **Destination** enters the vocabulary as the word for a top-level place in the product, which is how `client/src/v2` already uses it.

`/api/admin/users*` is deliberately excluded and keeps the global column, behind `requirePlatformAdmin`. It reads and writes `users`, which ADR-0006 exempts from Workspace scoping — no `workspace_id`, therefore no row-level security and no query scope — so it is a platform directory, not a Workspace surface. Authorizing it on the Workspace Role would let anyone who signs up and creates a Workspace list, re-role, reset the password of, archive and delete every account on the platform. Splitting the directory per Workspace was rejected as its own piece of work: the seam is `storage.getAllUsers`, not the gate. Until that lands, the global column is the only tenant boundary that surface has, and this decision records that it is holding one thing up rather than guarding Administration.
