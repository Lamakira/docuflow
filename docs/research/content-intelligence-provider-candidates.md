# Content-intelligence provider candidates

**Status:** Research input, not an architecture decision  
**Research date:** 2026-08-05  
**Supports:** GitHub issue [#3](https://github.com/Lamakira/docuflow/issues/3) and the backend architecture [map #1](https://github.com/Lamakira/docuflow/issues/1)

## Question and constraints

Which concrete candidates could support DocuFlow's full-text search, vector retrieval, transcription, and generative AI while preserving Workspace and Document Access boundaries?

The map fixes the following constraints: centrally operated multi-tenant SaaS; one primary EU region; GDPR compliance and SOC 2/ISO 27001 readiness; replaceable adapters where replacement cost is meaningful; controlled third-party AI processing; workspace policy and purpose limitation; auditability; configurable retention and contractual no-training guarantees; and complete core workflows when AI is disabled. This paper compares candidates but deliberately does **not** select a provider or target architecture.

## Executive synthesis

1. Search/retrieval and generation should remain separate decisions. The canonical authorization check belongs to DocuFlow. Every indexed chunk needs immutable provenance (`workspace_id`, source type/id, source revision, access scope/version), and every query must apply Workspace and Document Access constraints before material is returned or cited.
2. PostgreSQL full-text search plus pgvector is the lowest-complexity baseline and keeps filtering close to canonical data. Azure AI Search provides the broadest managed lexical/hybrid/semantic feature set among the candidates examined. Qdrant is a portable, vector-focused alternative with explicit multitenancy tools. The scale and relevance threshold for adding a separate index is an unresolved benchmark question.
3. For transcription, Azure Speech, Google Speech-to-Text V2, Amazon Transcribe, and OpenAI Audio all have credible EU-capable paths, but their retention/training defaults differ materially. OpenAI's European regional processing requires approved retention controls; Amazon Transcribe needs an explicit AI-services opt-out policy to satisfy no-training; Azure Speech has the clearest no-at-rest path for real-time audio.
4. For generation, direct OpenAI/Anthropic APIs maximize access to their native models; Azure Foundry, Amazon Bedrock, and Vertex AI provide stronger cloud-native identity/audit/model-catalog integration. EU availability must be verified **per model, feature, and deployment type**, not merely per vendor.
5. A DocuFlow-owned gateway contract is required regardless of whether its runtime is a thin application module, a self-hosted gateway such as LiteLLM, or a hyperscaler model plane. Provider control-plane logs do not contain DocuFlow's complete workspace/member/purpose context.

### Retrieval questions the architecture decision still needs to answer

- What corpus size, update rate, languages, query latency, filtered-recall target, and disaster-recovery objective are expected at 12 and 36 months?
- Is PostgreSQL-only quality sufficient for the first migration wave, with an outbox-fed secondary index added only after measured thresholds?
- Should Workspace isolation use shared indexes with mandatory filters, index-per-workspace for selected large workspaces, or a tiered model?
- How are deletions, membership/access changes, and source revisions propagated, verified, replayed, and reconciled?
- Are embeddings stored as rebuildable derivatives, and does each row record model/version, dimensions, chunker/version, source revision, and consent/policy version?

## Controlled gateway options

These are implementation families, not mutually exclusive provider choices.

### 1. Thin DocuFlow-owned gateway module

Expose one internal contract (`generate`, `embed`, `transcribe`) and implement provider adapters. It has the smallest infrastructure footprint and gives DocuFlow full control over policy and audit semantics. It requires building routing, retries, budgets, rate limits, streaming normalization, model capability discovery, and evaluation tooling. It is a strong incremental starting point if only one or two providers are enabled, but it must not leak provider-specific response types into domain modules.

### 2. Self-hosted LiteLLM Gateway behind a DocuFlow policy service

LiteLLM offers one OpenAI-compatible interface to many providers plus routing, virtual keys, spend tracking, guardrails, load balancing, and logging. Self-hosting preserves network placement and provider optionality, but introduces another privileged service, secrets store, database, upgrade/security-patch path, and licensing review for enterprise features. A recent security advisory demonstrates why pinned, verified images and prompt patching are operational requirements. LiteLLM can normalize transport; it should not make Workspace authorization decisions. [Official repository](https://github.com/BerriAI/litellm), [security advisories](https://github.com/BerriAI/litellm/security/advisories)

### 3. Hyperscaler model plane as gateway

Azure Foundry, Bedrock, or Vertex can provide a managed catalog, regional deployment policy, cloud IAM/private networking, quotas, and cloud audit integration. This reduces gateway operations and legal relationships but ties routing and feature availability to the selected cloud. Model APIs are only partially portable, and the same named model may differ by version, region, throughput mode, and supported features.

## Gateway controls that remain DocuFlow's responsibility

Before any external call, the gateway must:

- authorize the User's Capability in the Active Workspace and re-evaluate Document Access for every retrieved source;
- evaluate the Workspace's AI policy and the specific purpose (`search_embedding`, `transcription`, `summary`, `answer`, etc.);
- minimize/redact payloads where applicable and prohibit unapproved tool/grounding/file-store features;
- select only providers, regions, endpoints, models, and retention modes allowed by policy;
- attach an idempotency/correlation ID and enforce budgets, rate limits, timeouts, retries, and circuit breakers.

For every call, retain a content-minimized audit event containing workspace, actor/service principal, purpose, source identifiers/revisions, policy version, provider/region/model/version, retention mode, redaction result, timestamps, outcome, token/audio units, cost estimate, and provider request ID. Raw prompts/responses should not be copied into general logs. Citation output must refer back to authorized DocuFlow source revisions, and generated content must never broaden Document Access.

## Indicative cost model for the later decision

Provider list prices are volatile and exclude storage, egress, replicas, observability, support, taxes, commitments, and engineering. The architecture ticket should compare monthly scenarios using:

```text
retrieval = fixed search/vector capacity + indexed GB + replicas/backups + query/rerank units
embedding = changed chunks × tokens/chunk × embedding rate + retries
transcription = audio minutes × channel factor × model/feature rate
generation = input tokens + cached tokens/writes + output tokens + tools/grounding
operations = gateway/search/database compute + logs/traces + on-call and upgrade burden
```

At minimum model small, expected, and 10× workloads; include re-index/re-embedding events, deleted-content churn, EU/regional uplifts, minimum HA footprints, and a provider outage fallback. Cost attribution must be by Workspace and purpose so subscription limits can be enforced without recording sensitive content.

## Decision gates and recommended experiments

The architecture decision should remain open until these facts are available:

1. **Corpus benchmark:** representative multilingual Documents/Files with Workspace/access filters; measure lexical relevance, hybrid recall, filtered p95/p99 latency, ingest lag, deletion lag, and cost on PostgreSQL/pgvector, Azure AI Search, and Qdrant.
2. **Transcription benchmark:** consented French/English and relevant regional-accent audio; measure word error rate, diarization, names/domain vocabulary, latency, redaction, and total cost across shortlisted EU endpoints.
3. **Residency/legal verification:** DPA/subprocessor list, region/model/feature matrix, ZDR/no-training amendment eligibility, support-data handling, breach terms, deletion evidence, and whether metadata leaves the EU.
4. **Gateway spike:** the same DocuFlow contract against two model planes; validate streaming, structured output, retry/idempotency behavior, provider request correlation, policy denial, cost attribution, and failover without provider objects escaping the adapter.
5. **Failure drills:** stale membership/access change, source deletion during indexing, provider timeout after billable completion, malformed transcription, model withdrawal, key compromise, region outage, and reprocessing after policy changes.

## Research conclusion (not a selection)

The viable frontier is a deliberately composable stack: PostgreSQL/pgvector, Azure AI Search, and Qdrant for retrieval; Azure Speech, Google Speech-to-Text V2, Amazon Transcribe, and OpenAI Audio for transcription; and direct OpenAI/Anthropic or Azure Foundry/Bedrock/Vertex for generation. All require a DocuFlow-owned policy and audit boundary. The next architecture decision should choose each layer independently using measured corpus/audio results and executed EU retention terms, rather than selecting a single vendor suite by feature checklist.
